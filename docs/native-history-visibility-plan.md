# 近期原文保留与可逆原生隐藏：实施计划与验证记录

审查日期：2026-11-25。状态：实现及自动化回归已完成；真实酒馆人工冒烟尚未执行。

## 1. 目标与现状

改善现有“用记忆替换已归档原文”和“保留最近 N 轮原文”，不新增严格隐藏模式。N 是至少保留的最近完整剧情轮数，不是最多显示的轮数。N 从 3 增至 5，应恢复溯微隐藏的倒数第 4、第 5 轮；N 缩小，仅隐藏已有有效、连续且确认保存的记忆能够接替的旧原文。缺档、分组摘要跨界或来源无法验证时，允许实际保留多于 N 轮。

原消息正文、数组顺序、附件和 Swipe 数据保持完整；用户原生隐藏的消息仍由用户控制。沿用现有分层压缩，不增加固定 Token 预算裁剪。

## 2. 审查时发现的问题（实施前基线）

1. 当前 index.js:getCachedRoundIndex 仍按 chat 数组引用与 includeNativeHidden 缓存；CHAT_CHANGED 首次刷新前没有失效缓存。相同数组原地替换内容时，首个预览仍可能使用旧窗口。
2. history-builder.js:selectHistoricalEntries 已新增完整 turns 参数，但 buildChatHistoryReplacement 调用处仍未传入。不能仅补实参：同时要保留“摘要不可从中间裁切”的边界约束，否则 Math.min(end, limit) 会将整段跨界摘要当成局部覆盖。现有“5–8 轮分组 L0 跨进原文窗口时整组保留原文”的行为应继续成立。
3. refreshPromptInjection 会清空旧扩展提示并构建页面预览；没有 coreChat 时不修改宿主历史。因此现有 GENERATION_STARTED dry-run 分支只刷新页面，尚未向真实 dry-run 提示词补入记忆。
4. 酒馆在 interceptor 之前按 is_system 过滤源消息。新增原生隐藏后，如果覆盖范围缩小，仅在 interceptor 中调小 rawStart 无法找回已被宿主过滤掉的原文。需要在宿主过滤之前恢复必要的插件隐藏消息。
5. 原生 hideChatMessageRange 会切换 is_system、更新现存消息 DOM、刷新 Swipe 控件并保存整个聊天；它没有插件所有权字段。扩展上下文公开的是 saveChatConditional 的 saveChat 别名和 swipe.refresh，而非必然存在的 hideChatMessageRange。连续范围是调用粒度，不能描述为服务器只保存该范围。
6. 保存前后检查身份只能发现过期结果，不能自动保证一个等待后再读取全局 chat 的宿主保存包装器仍保存原聊天。适配层必须核实实际快照捕获时点，并区分保存确认、明确失败和结果未知。
7. 当前 widget-behavior 测试环境截掉了初始化代码，并默认替换 syncHiddenMessagesState；其持久化模拟主要保存元数据。只扩充现有用例不足以验证真实 CHAT_CHANGED、GENERATION_STARTED、原生隐藏保存和 Swipe 取消顺序。

## 3. 统一覆盖计划与安全边界

在现有 buildChatHistoryReplacement 基础上提取或复用无副作用的覆盖规划步骤。不要另写一套凭 lastProcessedMessageId 决定隐藏的算法。输入包含完整聊天、已确认保存的记忆快照、设置、canonical round index、生成类型、明确的生成来源边界和宿主工具调用能力；输出至少包括：

- 安全 rawStart、连续覆盖轮次、选中的摘要及其完整来源范围。
- 需要保留原文的来源窗口，以及实际允许插件隐藏的来源消息集合。
- 原文条数、记忆条数、Token 估算及缺档、跨界或来源失效的回退原因。
- 对应的聊天身份、聊天加载 epoch、内容/设置修订号，供应用阶段检查。

使用完整 canonical index 验证来源，用本次 generationEnd 限制可用事实。对正常生成，继续接收宿主已应用发出正则、附件等处理的 coreChat，不用扩展自行拼出的原始文本替换宿主加工结果。绑定索引时传播 canUseTools，并同步核对 host-prompt.js 的可见消息、深度与 Swipe 排除规则，保留其他扩展插入的无来源消息。

来源映射不可靠时保留原文或放弃该候选；不能用模糊文本匹配的结果证明可以隐藏楼层。空 coreChat、仅含其他扩展消息等情况也需要明确的生成边界，不能无条件回退到完整聊天末尾而纳入候选 Swipe 或未来状态。

覆盖规则：

1. 从最早需要接替的历史开始构建连续覆盖；遇到首个无法覆盖的轮次，原文从该轮完整窗口起保留，后续摘要不跨过缺口继续隐藏。
2. L0 需有清理套话后仍有效的内容，完整起止消息位置对应真实轮次窗口，且全段不超过生成边界；只有游标达到该处不构成覆盖证明。
3. L1–L3 与远期记忆同样验证完整来源范围、连续有效的 L0 来源，以及现有来源记录能够证明的有效性。编辑、删除、重总结或 Swipe 使来源失效时，相关派生摘要必须失效；不能只看时间线存在或轮次标签连续。缺少足够来源证明的旧摘要降级使用 L0/原文，不在查看时补总结。
4. 验证需要完整 turns；替换资格仍受原文边界限制。分组摘要跨进近期原文窗口时，按现有规则把 rawStart 回退到整组起点。不得把 5–8 的文本重新标注为 5–6，也不得把超出 generationEnd 的整段摘要截短后使用。
5. 在可达的连续覆盖路径中优先使用有效高层摘要。重叠候选不能贪心选择后造成断档；保持可确定、可重复的选择顺序。高层替换与固定记忆、可选召回分别去重。
6. 对 301–325 新建完整来源的 L1 正例，以及缺一个 L0、端点错误、来源过期、跨近期窗口、超出 Swipe 边界的反例；反例应退回有效低层摘要或原文。

## 4. 可逆原生隐藏与所有权

继续识别可恢复的旧 tiandao_hidden 标记，不再在每次同步中无条件迁移恢复。native-visibility.js 只负责可见性差异和所有权，接收覆盖规划已验证的消息集合或范围，不自行推导摘要覆盖。

每条消息的处理规则：

| 当前状态 | 目标状态与动作 |
| --- | --- |
| 原本可见、属于安全接替区域、无用户可见覆盖 | 写入插件所有权并隐藏 |
| 插件拥有的隐藏消息重新进入原文窗口 | 恢复可见并移除插件所有权 |
| 插件拥有的隐藏消息失去有效摘要接替 | 恢复可见并移除插件所有权 |
| 关闭引擎或关闭替换 | 恢复所有插件拥有的隐藏消息 |
| 用户或其他来源原生隐藏，缺少插件所有权 | 不接管、不恢复 |
| 仍带插件所有权但被外部改为可见 | 识别为手动取消隐藏，移除所有权并保存可见覆盖 |
| 已有用户可见覆盖 | 后续同步保持可见 |

用户可见覆盖沿用现有草稿中的 suwei_auto_hide_opt_out 或等效消息字段，只跟随对应消息，不按可移动的数组下标另存。调整 N、切档或重复同步不清除此覆盖；重新开启替换也不自动清除用户的明确选择。不增加新模式或额外开关。

宿主若在消息仍处于隐藏时重复发出隐藏操作，而未暴露操作者信息，无法可靠区分用户、其他扩展与本插件。计划仅承诺处理可识别的手动取消隐藏，不承诺推断不可观察的所有权转移。

以完整剧情窗口为单位隐藏，避免只隐藏一轮中的玩家输入或 AI 回复。开场白归属第一轮窗口，不单算一轮。工具调用及结果链在宿主仍需保留时整体保留，不能只靠某条消息存在 tool_invocations 就假定链条安全。

插件拥有的隐藏消息在 canonical index 中持续参与剧情；includeNativeHidden 继续只控制用户原生隐藏消息的现有参与规则。隐藏前后 aiTurns、round、window、摘要起止点不变。区分可见性修订与剧情内容修订；复用现有恢复签名对插件隐藏的归一化，避免纯 is_system 变动让有效摘要或待保存恢复点被误判为原文变化。

同步必须幂等：没有实际差异时不改 DOM、不刷新 Swipe、不保存。用户覆盖字段变化即使不改变 is_system，也要纳入持久化。

## 5. 事件顺序、设置与异步一致性

统一使用按聊天身份串行或合并的协调入口，协调覆盖规划、可见性应用、缓存失效、预览发布和保存。禁止多个入口各自启动无身份保护的后台保存。

聊天身份至少区分单聊/群聊、角色或群组以及聊天文件；不要仅以文件名或 chat 数组引用认定同一聊天。每次异步续执行均检查聊天身份、加载 epoch、消息对象/内容修订、设置修订与目标记忆引用，覆盖 A→B→A 的情况。

- CHAT_CHANGED：入口立即递增加载 epoch、取消旧任务和临时 dry-run 注入、使 round cache 失效；这些动作发生在 getChatMemory、任何 await、可见性规划和首次预览之前。随后基于当前聊天重算，再发布预览。
- 设置变化：更新设置并失效相关计划，先完成必要恢复，再用新状态刷新预览。特别修改“恢复历史原文”按钮：先关闭替换，再执行恢复，避免沿用旧的先同步后关闭顺序。
- 摘要保存：仅在记忆确认保存且来源仍有效时扩大隐藏范围；待保存 draft、未确认结果或失败不得取得新的隐藏资格。失败后不循环补总结。
- 编辑、删除、重总结、导入、清空和恢复记忆：先按现有规则处理来源及派生摘要失效，再恢复缺少接替的插件隐藏原文，然后重算计划与预览。仅有有效摘要被移除，也要触发恢复。
- 正常生成与 dry-run：利用宿主等待的 GENERATION_STARTED，在构建 coreChat 之前完成本次生成需要的原文恢复和同步。该入口只计算现有数据，不触发补总结或 Embedding。interceptor 继续处理正常生成的加工副本。
- Swipe、regenerate、continue 等：本次生成计划使用对应的实际来源边界，不把候选内容当已提交剧情。生成结束、失败或取消后等待宿主真实 Swipe 恢复完成，重新读取 mes、swipe_id、长度和状态再同步。不能只收到 GENERATION_STOPPED 就假设回滚已经完成，也不能仅等固定毫秒数后沿用旧计划。
- 非活动聊天：不修改当前 DOM、当前提示词或复用数组中的新聊天消息。尚未完成的保存结果按原身份保留，回到对应聊天后重验或重算。

缓存键至少包含加载 epoch/聊天身份、内容修订与 includeNativeHidden；显式失效仍需覆盖初始化、编辑、删除、追加、Swipe、隐藏/恢复和相关设置变化。避免每个消息循环内重建整个 round index。

## 6. dry-run 与页面预览的落地要求

GENERATION_STARTED 是早期协调入口，本身没有宿主 coreChat 参数；不能把“await refreshPromptInjection”视为已经完成 dry-run 注入。

先做宿主兼容性验证，再接通原生自动隐藏：

1. 在实际宿主流程中验证 dry-run 的注入通道。优先通过可用的公开提示词接口，将规划选中的历史和状态内容映射到正确位置；需要操作消息数组时，使用宿主可等待且公开携带该数组的事件。Chat Completion 可检查 CHAT_COMPLETION_PROMPT_READY；其他后端需验证其对应路径，不能因一个后端通过就声称全部支持。
2. 桥接仅在 dryRun 为真时工作，正常路径仍由 interceptor 注入。每次正常生成前清理所有本插件临时桥接 key；取消、失败、切档、关闭替换后同样清理。重复 dry-run 不叠加副本。
3. 保持正常方案的聊天历史语义、system/narrator 角色和状态账本的来源位置。不能把整个 plan.text 作为一个任意 Depth 提示塞进去，造成近期原文重复或旧状态覆盖新剧情。
4. 单次流程共享同一份覆盖与选择结果。预览、dry-run 与正常发送的核心摘要范围、原文窗口和边界回退一致。可选向量召回仅用已有查询缓存或本地检索；冷缓存时也不发 Embedding。正常发送若原本允许新向量查询，其新增可选细节不应被宣称为免费预览已完整展示。
5. 常驻预览显示设置 N、实际连续记忆覆盖、保留的原文条数/轮数、记忆条数与估算 Token；因缺档或分组跨界多保留原文时显示原因。说明这是聊天历史区块，不冒充角色卡、世界书、预设及宿主最终截断之后的完整请求。
6. 对打开聊天、设置刷新、常驻预览与 dry-run 显式传递禁止外部请求的选项，不能仅依赖当前调用链“恰好不会总结”。用请求计数或桩断言扩展发起的总结与 Embedding 均为零；本地模块加载、宿主必要的聊天保存/回读不属于此禁令。

若某受支持宿主路径不能安全实现 dry-run 桥接，应保留原文并报告该路径未完成；不得先隐藏原文，再把“只有近期原文、没有记忆”的 dry-run 当成功。这是实施验收门槛，不新增用户模式。

## 7. 宿主适配与消息持久化

在 index.js 设置窄适配层，复用 host-persistence.js 的确认状态：

- 能取得并验证宿主 hideChatMessageRange 时，仅对实际变化的连续范围调用；先同步所有权字段，使宿主保存同时包含标记。该接口内部已经保存，不再无条件追加一次 saveChat。
- 兼容分支按相同语义更新 is_system、已存在的 .mes[mesid] DOM 属性和 ctx.swipe.refresh；对同一批差异尽量合并保存。宿主通常保存整个聊天，连续范围仅减少无效调用和 DOM 更新。
- 宿主接口不存在或不能保证其写入语义时，不接管不安全的原生隐藏；保留可用原文与现有生成副本替换能力，并明确兼容性缺口。
- 在开始变动/保存前固定原聊天读取目标、预期字段快照、消息位置及内容身份。核实保存入口是否在首次 await 前捕获目标与完整请求数据；仅有全局 saveChatConditional 包装器时，不能因调用前后身份相同就认为已绑定原聊天。
- 不把切档后的结果解释为当前聊天成功；不把异步失败后的旧补丁按下标应用到新 chat。来源一致性检查失败时停止该批继续操作。
- 回读验证原聊天中的 is_system、tiandao_hidden 与可见覆盖字段的存在性和值，并验证消息内容身份，避免同一个下标换了消息却误确认。按实际单聊/群聊返回结构解析 header 与消息，不假设所有响应都固定有一行 header。
- confirmed 才发布保存成功。failed 表示明确失败或读回不一致；unknown 表示切档、网络回读失败或无法证明。两者都不能静默视为已落盘。
- 回滚仅针对仍与该批预期消息及新状态相符的插件变更，保留其间的新编辑和用户隐藏操作。unknown 不盲目反向保存；保留待核实信息并在对应聊天恢复后重验，避免写回旧状态覆盖新状态。
- 保存队列合并同一身份、同一有效修订的请求，防止生成事件、设置和宿主保存事件互相触发无限同步。
